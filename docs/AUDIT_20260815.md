## 3. Notable findings requiring judgement, not just a checklist tick

### 3.1 V51 vs. V06/V59: the verifier bans the file it also requires

`check_V51`'s `BLOB_EXTS` tuple includes `.pt`. Every tracked `.pt` file is therefore flagged as
"junk" — including `weights/best.pt`, which V06 and V59 (both PASS) require to be tracked, and
which is the single most important deliverable in the repo per CLAUDE.md PD4. This is an
internal contradiction between two Tier-0/Tier-4 checks in the **pinned, immutable** verifier.
Per Prime Directive 1, this cannot be fixed by editing the checker — it must be logged in
`docs/BLOCKERS.md` (not yet present there) and escalated to a human decision: either widen the
blob-extension list's exemption to cover the one path `weights/best.pt` (analogous to the
existing narrow `sample_inputs/*.npy` exemption for V51), or accept V51 as permanently red.
**Not resolved by this audit — audit-only, no code changes made.**

### 3.2 V32 false positive traced to a venv-naming edge case

`check_V32`'s exclusion is `if ".venv" in py.parts: continue` — an exact path-segment match, not
a substring match. This machine's project venv is named `.venv-mac` (created this session,
listed in `.gitignore`), so the exclusion does not match it, and the check walks into
`.venv-mac/lib/python3.11/site-packages/lpips/__init__.py`, a third-party package, and finds a
plain `cv2.imread(` there. Confirmed directly:
```
grep -rl "cv2.imread(" .venv-mac --include="*.py" | xargs grep -L IMREAD_UNCHANGED
→ .venv-mac/lib/python3.11/site-packages/lpips/__init__.py
```
No `cv2.imread(` call exists anywhere in the repo's own source (`grep -rn "cv2.imread(" . ` outside
`.venv-mac` returns nothing). This is **not a shipped-code defect** — but it demonstrates the
check is fragile to venv-directory naming, which is worth one line in `docs/BLOCKERS.md` so a
future run under a differently-named venv doesn't get misread as a real regression.

### 3.3 Dataset-dependent checks (V25/V29/V33/V34) — inconclusive, not re-confirmed

These require `KLA_DATA_ROOT` and a real training subprocess. In this session:
- With the dataset root misconfigured (pointed one level too deep), all four failed with a
  clear, correct "no train/GT directory" error — expected behaviour, not a bug.
- With the root corrected, a background `verify_all.py --strict` run still reported the same
  wrong-root error inside the child `train.py` process, despite a standalone diagnostic
  (`resolve_data_root(None)` with the same env var) resolving correctly and finding `train/GT`.
  This is most likely an artifact of how the long-running backgrounded shell invocation carried
  (or failed to carry) the inline `KLA_DATA_ROOT=...` prefix through this session's tooling —
  not something I was able to fully pin down before the deadline pressure made further CPU-bound
  reruns (each `--overfit`/`--smoke` pass took 10+ minutes on this CPU-only Mac) not worth the
  time relative to the branch-integration gap in §0, which is strictly higher priority.
- `docs/decisions.md` D26 claims these were cleared at 43.33 dB, but that entry predates this
  session and was measured on a different machine/branch lineage. **I did not independently
  reconfirm it this session and it should not be cited as current-state proof.**

**Recommendation:** rerun `KLA_DATA_ROOT=/Users/shanmukhsai/Downloads python scripts/verify_all.py --strict`
in a foreground terminal (not backgrounded) with enough time budget (~30–60 min) before final
submission, and treat the result as the authoritative current state.

### 3.4 `weights/README.md` is stale

Still reads "**No checkpoint exists yet. Training has not been run.**" — written at bootstrap and
never updated after Phase 1 training completed (`weights/best.pt` has existed, tracked, with a
matching SHA256, since before this session started). Low severity (doesn't block scoring — a
reviewer would still find the actual file), but it's a documentation-currency gap owned by
`docs-scribe` and should be fixed alongside the README/runtime-report merge in §0.

### 3.5 README.md on the best-model branch doesn't mention the best model

`codex/residual-ls5-refinement`'s `README.md` (inherited unchanged from `train-first-model`)
still reports only the LS-5 result (26.3277 dB) as "Ours". The 27.7625 dB (`r1_nb4`) and

different branches that were never reconciled.

## Step 2 — Was the 28.04 dB vs 28.79 dB comparison even valid to make?

Before trusting either number: confirmed **byte-identical** `src/metrics.py`, `scripts/evaluate.py`
and `configs/split_val.txt` between the two branches (`git diff 9a0a4dd origin/main --` on all
three — empty; sha256 of `split_val.txt` matches on both sides). Both lines therefore:
- use the same pinned metric settings (PSNR `data_range=1.0`; SSIM `gaussian_weights=True,
  sigma=1.5, use_sample_covariance=False`; LPIPS `net='alex'`, grayscale→3ch, `[-1,1]`),
- score the identical 400-image committed split,
- score **reloaded on-disk `.npy` artifacts**, not in-memory tensors (V30 discipline) — origin's
  own STATE.md narrative explicitly describes disk-verification via `make_baselines.py` +
  `evaluate.py` for their 28.0394 dB number, matching this session's own protocol.

Conclusion: the two numbers were computed the same way and are directly comparable on paper.
Step 3 re-verified this empirically rather than trusting it.

## Step 3 — Re-scored both checkpoints under one harness

`git worktree add ../semi-origin-check origin/main` — a clean checkout of the teammate's tip,
used only to load their checkpoint with their own (compatible) `src/model.py`, never mixed with
this session's tree.

1. Generated predictions from origin's checkpoint via `scripts/make_baselines.py --baselines
   final` in that worktree, pointed at this session's `C:\kla-data`, run on this session's RTX
   4060.
2. Scored with `scripts/evaluate.py` (identical file either side): reproduced origin's
   self-reported **28.0394 / 0.74804 / 0.29571** exactly — not a measurement artifact, a real,
   reproducible number.
3. Direct paired comparison (`src.metrics.paired_compare`, the same statistic `check_V28` uses)
   between this session's predictions (`results/baselines/final`) and origin's, same 400 images:

   | metric | mean diff (ours − theirs) | t | images better (ours) | verdict |
   |---|---|---|---|---|
   | psnr | +0.7471 | 21.62 | 378/400 | **win** |
   | ssim | +0.0348 | 26.13 | 397/400 | **win** |
   | lpips | −0.0424 | −6.38 | 271/400 | **win** |

4. Param counts confirmed via each side's own `build_model` + `count_parameters`: this session's
   checkpoint 388,225 params (NAFSR w48n16, all trained from scratch); origin's checkpoint
   246,529 params (NAFSR w48n8, `padding_mode="replicate"`, stem/head initialised from a
   closed-form LS-5 fit, body trained as a residual correction).
5. Wall-clock, same RTX 4060, same methodology (bf16, channels_last, forward-only):

   | | 128→256 | 256→512 |
   |---|---|---|
   | this session's checkpoint | 21.306 ms/img | 34.331 ms/img |
   | origin's checkpoint | 9.156 ms/img | 18.286 ms/img |

   Origin's checkpoint is ~2.3×/1.9× faster — real, and recorded as a genuine Pareto trade-off,
   not dismissed. SPEC states no throughput floor and does state a three-metric quality rubric,
   so quality decided which checkpoint ships (D49).

**This session's checkpoint wins all three metrics, paired, with high significance
(`|t| ≫ 1.96` on every metric).** Verdict: ship it, per `docs/decisions.md` D49.

Generated by `scripts/benchmark_runtime.py` (no subcommand -- it is a single flat CLI, see
Method below for the exact invocation). **Device: NVIDIA GeForce RTX 4060 Laptop GPU** -- every number below was measured on this GPU, never an H100. Timing is external: each `e2e` and `imports` row wraps a full `subprocess.run([python, inference.py, ...])` from outside the process (interpreter start, imports, CUDA init, checkpoint load, disk IO and compute all included), not an internal timer around the forward pass -- that is what V38 requires and what makes the startup cost visible instead of hidden.

## Current shipped checkpoint, current default batch_size=4 (2026-08-18, `docs/decisions.md` D74)

`weights/best.pt` is the Phase 3 fine-tune (NAFSR width=64, num_blocks=32, FiLM+uncertainty,
1,393,938 params). `inference.py`'s `--batch_size` default changed from 32 to 4 this session
(see the batch-size sweep section below) after that sweep showed batch 4 measurably beats 32
end to end on this hardware. **This headline number is measured with NO `--batch_size` flag
passed at all** — i.e. exactly the command KLA actually runs — not with an explicit override:

**Local CUDA external-process benchmark: 400 images, median 20.62 s (19.40 img/s), batch 4
(inference.py's real default, unforced), bf16, n=5 repeats (20.36, 20.48, 20.62, 20.66, 20.76 s).**

Regenerated by `scripts/benchmark_runtime.py --input_dir C:\tmp\val400_lr --precision bf16
--repeats 5` (no `--batch_size` — see the bug note directly below for why that matters).

**A real bug was found and fixed while regenerating this number.**
`scripts/benchmark_runtime.py` had its own hardcoded `--batch_size` default of 32 and
**always** forwarded `--batch_size <value>` explicitly to the `inference.py` subprocess
(`_run_once`, previously line 43) — so running the benchmark script "with no `--batch_size`"
never actually exercised `inference.py`'s own default; it silently pinned every un-overridden
run to 32 regardless of what `inference.py`'s shipped default was. This was caught because,
immediately after changing `inference.py`'s default to 4, a bare run of the benchmark script
still measured ~28.85 s median (matching the *old* batch-32 number, not the new batch-4 sweep
result of ~21.97 s) — a discrepancy that would not exist if the tool actually measured the
real default. Fixed: `--batch_size` on the benchmark script now defaults to `None` and the
flag is only forwarded when explicitly passed, so an un-overridden run genuinely measures
whatever `inference.py` itself defaults to. Confirmed fixed: re-run below matches the explicit
`--batch_size 4` measurement (median 19.99 s) to within normal session variance.

Architecture is byte-identical in parameter count to the checkpoint below, so this is expected
to be roughly the same throughput modulo normal session-to-session variance on this laptop
GPU (documented immediately below as a real, previously-observed measurement caveat on this
same hardware — not new to this run).

|---|---|---|---|---|

| **Current shipped (1,393,938 params)** | 31.28 s | 31.12--31.42 s | 1.0% | **12.79** |

Under controlled, back-to-back, equally-quiet conditions, **the bigger checkpoint is
measurably slower — +54.8% wall-clock, a real throughput cost, not an artifact.** This is the
physically expected result for 3.6x more parameters and matches this project's own
memory-bandwidth-bound finding (D21): it was NOT observed in the original comparison only
because the old absolute number (8.3 img/s) was contaminated by a 681%-spread session, not
because the new checkpoint is actually faster in general.

**A separate, disclosed methodology caveat this comparison surfaced:** this controlled
same-session run of the current checkpoint measured median 31.28 s, while the standalone
17.3 img/s (23.19 s) headline above it — measured in an EARLIER session — does not even
overlap in range with this run's 31.12--31.42 s. Both are genuine measurements; the
discrepancy is consistent with RTX 4060 Laptop GPU boost-clock/thermal-state variance across
sessions (confirmed idle-clock throttle state present between runs via `nvidia-smi`), not a
methodology error in either one. **Conclusion: absolute img/s figures on this laptop GPU
should not be compared across different measurement sessions; only same-session,
back-to-back comparisons (like the table above) support a relative claim.** Full raw output:
`results/eda/runtime_old_ckpt_b2.md`, `results/eda/runtime_new_ckpt_b2.md`.

The detailed batch/precision/memory-format sweep, profiler breakdown, and import-cost tables
below were measured against **the D49 (388,225-param) checkpoint/architecture size**, not the
one currently shipped. Re-measuring that full sweep at the new size is a documented follow-up

## Batch-size sweep -- END-TO-END, current shipped checkpoint (2026-08-18, throughput-optimizer task)

**Supersedes the batch-size *conclusion* of the isolated-forward-pass table below for the
question "what should `--batch_size` default to". Different methodology, not just a different
checkpoint:** this sweep times the WHOLE PROCESS externally via
`scripts/benchmark_runtime.py` (`subprocess.run([python, inference.py, ...])` -- interpreter
start, imports, CUDA init, checkpoint load, disk IO and compute, exactly what KLA's harness
measures), against the currently shipped checkpoint (NAFSR width=64, num_blocks=32,
FiLM+uncertainty, 1,393,938 params, `weights/best.pt`). The table below it is an isolated
forward-pass-only measurement (no subprocess, no startup cost) against the OLD, superseded
388,225-param checkpoint -- kept for its own record (precision/memory-format comparisons are
still informative), but its batch-size numbers must not be used to pick the shipped default;
use this section for that.

**Method:** `scripts/benchmark_runtime.py --input_dir <dir> --out <scratch file> --repeats 1
--batch_size <b> --precision bf16`, invoked once per (round, batch size) pair in a single
continuous session, round-robin interleaved across batch sizes {4, 8, 16, 32, 64} -- 5 full
rounds, so no batch size's repeats are clustered at one point in session/thermal time. This
matches the project's own documented discipline (below: "only same-session, back-to-back
comparisons... support a relative claim") applied to batch size specifically, not just
checkpoint comparisons. Medians are over n=5 interleaved repeats per batch size.

### 128 -> 256 (`test_NoisyLR`-shaped input, `C:\tmp\val400_lr`, 400 images)

| batch | median external wall-clock | img/s | all 5 repeats (s) |
|---|---|---|---|
| 4 | **21.97 s** | **18.21** | 20.80, 21.59, 21.97, 24.08, 61.09 |
| 8 | 24.11 s | 16.59 | 23.29, 23.55, 24.11, 34.57, 152.53 |
| 16 | 26.03 s | 15.37 | 23.52, 24.95, 26.03, 36.48, 61.45 |
| 32 (current default) | 32.19 s | 12.43 | 28.42, 30.85, 32.19, 35.18, 87.38 |
| 64 | 36.66 s | 10.91 | 31.00, 31.08, 36.66, 115.82, 152.25 |

Monotonic: throughput falls as batch size rises, across the whole tested range. **Batch 4 beats
the current default of 32 by 31.8% lower wall-clock (46.5% higher throughput)**, holding in 4
of the 5 interleaved rounds (round-by-round batch-4-vs-batch-32: 21.59<32.19, 20.80<35.18,
21.97<30.85, 24.08<87.38, all batch-4-faster; the one exception, round 5, is a batch-4-side
outlier -- 61.09 s vs that round's normal 28.42 s for batch 32 -- not a batch-32 win). Every
batch size's repeat set includes 1-2 outlier repeats several multiples of the median (152.53 s,
152.25 s, 115.82 s, 87.38 s, 61.45 s, 61.09 s) consistent with this laptop GPU's
already-documented cross-run thermal/driver-contention variance (see the 681%-spread N=400
headline and the "48269.4 ms... spread 681.4%" figure elsewhere in this file) -- medians, not
means, are reported for exactly this reason, and batch 64 has the most such outliers (2 of 5),
compounding its already-worst median.

|---|---|---|---|
| 4 | **63.24 s** | **6.33** | 63.07, 63.14, 63.24, 63.78, 232.72 |
| 8 | 63.91 s | 6.26 | 63.60, 63.67, 63.91, 64.36, 120.60 |
| 16 | 65.00 s | 6.15 | 64.86, 64.91, 65.00, 65.47, 98.25 |

Same monotonic trend at 4x the pixel count. **Batch 4 beats batch 32 by 18.1% lower wall-clock
(22.1% higher throughput)** at this resolution too. Round 1 was uniformly elevated across every
batch size (232.72, 120.60, 98.25, 103.44, 88.14 s -- a session cold-start effect: cuDNN

first for every one of them); rounds 2-5 are tight (spread <2% for batch >= 8, ~1.1% for batch
4), which is why the reported median is robust to it and unaffected by which round the cold
start landed in.

### Conclusion and recommendation

**Change `inference.py`'s `--batch_size` default from 32 to 4.** Reproduced at both tested
resolutions, in one continuous interleaved session, n=5 medians per point, with the win holding
even after accounting for this GPU's known outlier behavior (majority-of-rounds check above).
Batch sizes below 4 were out of scope for this sweep (the task specified {4, 8, 16, 32, 64}) and
are not claimed to be better or worse. This is a recommendation only -- **`inference.py` was not
edited**, per this task's file-ownership boundary; see the proposed diff below.

## Method

- Timing is taken **externally around the whole process** (`subprocess.run([sys.executable, "inference.py", ...])`), not by an internal timer around the forward pass.
- Every number above is labelled with the device it was measured on: **NVIDIA GeForce RTX 4060 Laptop GPU**. No H100 number appears anywhere in this file.
- Reproduce: `py -3.12 scripts/benchmark_runtime.py --input_dir <dir-of-.npy-inputs> --out results/runtime_report.md --repeats 5 --batch_size 4 --precision bf16` (the script's real CLI has no subcommands -- no `all`, no `report`, no per-stage resume/skip; every invocation is one flat run of N repeats at one fixed config, and `--out` is overwritten in full each time, not merged or resumed).
